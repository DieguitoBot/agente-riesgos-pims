BASE EXCLUSIVA DEL AGENTE DE RIESGOS PIMS

La aplicación consulta PostgreSQL para ISO, ley y contexto institucional. No necesita
PDF, Markdown ni FAISS para recuperar documentos. Combina BM25 con similitud
semántica cuando hay vectores del modelo configurado y Ollama está disponible.
Los vectores se almacenan en PostgreSQL (double precision[]). Si Ollama falla,
se informa el uso exclusivo de términos. PIMS_BUSQUEDA_SEMANTICA=0 desactiva
la llamada al modelo; RAG_EMBED_MODEL debe coincidir con el modelo indexado.

Desde agente_riesgos_pims_v2:
  .venv/bin/python -m db.local iniciar
  .venv/bin/python -m db.migrar
  .venv/bin/python -m db.migrar --inventario
  .venv/bin/python -m rag.indexar  # solo si faltan embeddings
  ./iniciar.sh

El clúster local vive en ../.datos/postgres, con socket privado en ../.datos/socket,
puerto lógico 55439 y sin escucha TCP. No usa ni modifica el servicio PostgreSQL
del sistema. Detener solo esta instancia: .venv/bin/python -m db.local detener
Reiniciar tras reiniciar el equipo: .venv/bin/python -m db.local iniciar
El directorio privado limita acceso por usuario del sistema operativo; los procesos
de otros agentes que ejecuten con el mismo usuario del SO no constituyen una frontera
de seguridad. Para aislamiento entre personas/servicios usar proyecto propio y credenciales.

.env contiene las conexiones privadas. La aplicación usa pims_lector (SELECT);
la importación usa la conexión administrativa. No publicar .env, .datos o volcados.
En local, la autenticación usa el socket accesible solo al propietario del directorio.

Organización:
  documentos: normativa, institucional, proyecto, reporte, evidencia.
  fragmentos: secciones ISO, artículos de ley y extractos institucionales.
Cada documento preserva original binario, texto, SHA256 y ruta de procedencia.
Las capturas se conservan como evidencia, sin inventar una transcripción OCR.
Reportes e instrucciones del proyecto NO entran en la recuperación normativa.
Los dos textos de la ley se conservan con procedencias distintas; no se asume que
sean iguales. La vigencia y exactitud de fuentes importadas siguen pendientes.

Migración:
Lista explícita de fuentes dentro de este repositorio; no se exploran proyectos vecinos.
Se procesa todo antes de abrir la transacción. Repetir actualiza por clave sin duplicar
registros y actualiza sus fragmentos en una sola transacción. Conserva los
vectores cuando el fragmento no cambia; invalida solo los vectores de texto cambiado. Los originales locales
se conservan como respaldo histórico, no como fuente operativa de la aplicación.
No ejecutar migrar después de editar el contenido directamente en la base si se desea
conservar esa edición: la importación reemplaza la versión de esas mismas claves.
No hay eliminación automática de documentos ausentes en disco.
Para importar el índice FAISS histórico una única vez: python -m db.importar_indice.
Solo se aceptan vectores con metadatos y texto idénticos a lo ya migrado.
requirements-rag.txt contiene las dependencias opcionales de importación histórica.
Inventario consultable en GET /api/documentos; la API devuelve 503 si la base falla.

Pruebas unitarias: .venv/bin/python -m unittest discover -s tests
Pruebas contra la base dedicada (incluyen reimportación del corpus):
  PIMS_TEST_DATABASE=1 PIMS_BUSQUEDA_SEMANTICA=0 .venv/bin/python -m unittest discover -s tests

Supabase:
1. Conectar la integración y crear/seleccionar un proyecto EXCLUSIVO de este agente.
2. Obtener la conexión PostgreSQL directa o Session pooler en Connect; usar SSL.
   https://supabase.com/docs/guides/database/connecting-to-postgres
3. Configurar PIMS_DATABASE_ADMIN_URL en .env, ejecutar python -m db.migrar.
4. Crear usuario pims_lector LOGIN con contraseña privada y permisos de lectura
   siguiendo permisos_lector.sql. Configurar PIMS_DATABASE_URL con ese usuario.
   En un pooler Supabase, el usuario incluye el sufijo del proyecto.
5. Verificar inventario, fuentes y pruebas antes de dejar de usar la base local.
No añadir pims_riesgos a los esquemas expuestos por la API pública. RLS está activado;
no hay políticas anon/authenticated. La conexión privilegiada nunca va al navegador.
No se ha aprovisionado alojamiento en Supabase por el mero hecho de preparar este código.

Copias de seguridad: usar pg_dump en formato custom contra la base exclusiva y guardar
el volcado en almacenamiento privado; comprobar restauración en otra base dedicada.
Las instrucciones antiguas en README/RAG describen el flujo histórico basado en archivos;
este archivo describe la operación PostgreSQL vigente.

PGADMIN 4 LOCAL
Instalado en ../.datos/pgadmin-venv (entorno separado de la aplicación).
Configuración propia en ../.datos/pgadmin. Versión instalada: 9.19.
Abrir desde agente_riesgos_pims_v2: ./abrir_pgadmin.sh
Panel: http://127.0.0.1:5050
El lanzador inicia también nuestro PostgreSQL si está detenido.
Ctrl+C en esa terminal cierra solo pgAdmin; no detiene PostgreSQL.

Conexión registrada: Agente de riesgos PIMS > PIMS - Riesgos (local).
Ruta en el explorador: Databases > pims_riesgos > Schemas > pims_riesgos > Tables.
Tablas: documentos y fragmentos. Clic derecho > View/Edit Data > All Rows.
El servicio pims_local usa únicamente nuestro socket y el usuario pims_admin.
Modo de escritorio local sin cuenta de pgAdmin; no guarda contraseñas y no usa
el llavero del sistema. No está expuesto a la red. Administra solo nuestro clúster.
La base SQLite de pgAdmin conserva sus preferencias; los documentos del agente
siguen en PostgreSQL.

Para reinstalar pgAdmin sin cambiar las dependencias del agente:
  python3 -m venv ../.datos/pgadmin-venv
  ../.datos/pgadmin-venv/bin/pip install --no-cache-dir pgadmin4==9.19
  ./abrir_pgadmin.sh
